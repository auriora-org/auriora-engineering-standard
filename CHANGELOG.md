# Changelog

All notable changes to the AURIORA Engineering Standard (AES) are documented in this file.

The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.1.0/). AES releases use semantic versioning as required by [AES-VER-001](./docs/05-interfaces-and-versioning.md#aes-ver-001-semantic-versioning-for-released-contracts): `MAJOR` for incompatible normative change, `MINOR` for backward-compatible normative addition, `PATCH` for clarification or defect correction. While the major version is zero the standard is in pre-Release development, which AES-VER-001 leaves informally versioned: an incompatible normative change increments `MINOR` and says so in its entry, and `1.0.0` follows when the Platform's interface specifications leave Draft. Entries record normative changes with their requirement identifiers; editorial changes are either omitted or explicitly marked as editorial, per [AES-GOV-011](./docs/08-decisions-and-governance.md#aes-gov-011-standard-change-record).

## [0.9.0] - 2026-09-18

### Changed — incompatible

- **The standalone M8 3-position AEL IN / AEL OUT connectors are withdrawn; AEL links are carried in the Module Port** ([EDR-011](./docs/edr/EDR-011-module-external-interfaces-and-power.md), superseding items 8 and 9 of EDR-008). The [AEL specification](./docs/interfaces/ael.md) moves from `0.1` to **`0.2`**: §3 Physical Layer is rewritten — AEL IN and AEL OUT are the `AEL_IN_P`/`AEL_IN_N` and `AEL_OUT_P`/`AEL_OUT_N` pairs of the M8 8-position Module Port with the port's `GND` as reference, connected only by the AURIORA Link Cable, which crosses OUT to IN; direct operation is 1:1; a Hub-to-Hub link port is a Module Port connector whose cable carries a link in each direction; `AEL IN`/`AEL OUT` name links, not enclosure connectors. §2, §4 (protection and isolation wording), §8 and §8.6, the §9 Physical row and §10 are updated; the open gender/keying/cross-mating item is closed by the withdrawal. Electrical layer, frame, identifiers, timing reference and router are unchanged.
- **[Architecture §7.1](./docs/03-architecture.md#71-the-module-port)** no longer states that the Module Port does not replace standalone AEL ports; it is rewritten around the settled Module Port (below). **[Architecture §3](./docs/03-architecture.md#3-module-design)**: a Module reaches a Hub or a peer through its single Module Port, and AEL links are carried in it. **Terminology §3**: *Module Port* redefined; *Module Control Link*, *Module Hub* and *Hub-to-Hub AEL link* updated.

### Added

- **Module Hub host-facing interface and stored object retrieval** ([EDR-010](./docs/edr/EDR-010-hub-host-facing-interface-and-stored-object-retrieval.md)), resolving the host-facing transport left open by EDR-007/EDR-008 and the bulk-data path left open by EDR-008/EDR-009. Additive; MCI still has no version number.
  - `AES-HUB-003` (host-facing interface and traffic separation) in [Architecture §7](./docs/03-architecture.md#aes-hub-003-host-facing-interface-and-traffic-separation): a Module Hub provides a **host-facing interface** through which the system host reaches the Hub's own management and, via the `MCL` concentrator, the MCI of every Module on its Module Ports; it is neither a Module Port nor a Hub-to-Hub AEL link and consumes neither; it is an MCI transport binding, so a Module behind a Hub is operated with the same semantics as on a cable; it carries no AEL frames; where realized as USB the Hub is the USB device and the computer the USB host; the Hub forwards MCI including retrieval without interpreting it and buffers no more than the responses to outstanding requests; a control operation to any port during a bulk transfer is served within one chunk plus binding overhead and no bulk transfer holds the host link or an `MCL` link longer than one chunk; the AEL router's timing contract holds under bulk MCI load; the host-facing interface is not the power source of Module Ports or of the router, and powering the Hub itself from it is a documented product decision. §7 gains the introductory text and the `MCL` cascading paragraph notes that retrieval is end-to-end and independent of that decision.
  - `AES-MCI-008` (stored object retrieval) in [Interfaces and Versioning §5](./docs/05-interfaces-and-versioning.md#aes-mci-008-stored-object-retrieval): a Module MAY declare **stored object retrieval**, SHOULD where it records locally, and documents the alternative where it does not; the inventory lists recordings, event logs, diagnostic records and committed Assets and Sessions with identity, type, completion state and, once complete, size and whole-object integrity value; a **recording** additionally carries run and run segment, deployment identity, Session identity and integrity value, local-time and sample-index range, data format identifier and version and producing firmware version, and belongs to exactly one segment; reads by identity, offset and length in chunks within the declared maximum, each response naming object, offset and length; completed objects are immutable, readable in any order and resumable from any offset without renegotiation, the Module holding no retrieval state and never pushing; vanished or changed objects refused with a defined error; optional reads of an in-progress recording with a stable prefix; a retrieval is complete only when the assembled object matches the inventory's integrity value, chunk integrity being the binding's job; retrieval changes no state, configuration, policy or stored object, is available at least in `IDLE` and `COMPLETE`, never uses AEL, and during `ARMED`/`RUNNING` either does not degrade acquisition, actions or timing or is refused; read-only — deletion is a separately declared operation and nothing is discarded implicitly except under *overwrite oldest*; the binding defines its chunk bound and serves a control operation within one chunk plus overhead.
  - `AES-MCI-003`: the minimum capability list gains **local recording** and **stored object retrieval**, with the maximum chunk length and in-progress readability as the latter's limits. `AES-AEL-005`: the router's documented figures hold while MCI traffic, bulk transfer included, passes through the same device. §5 introduction: MCI also carries the Platform's bulk traffic in both directions as bounded low-priority chunks. §5.1: the direct local transport is also the Hub's host-facing interface.
  - [Architecture §3](./docs/03-architecture.md#3-module-design): a Module that records locally exposes its recordings as stored objects through the same control interface, so a recording made alone and one made under a Hub are read the same way.
  - **Terminology §3**: new supporting terms **host-facing interface**, **stored object**, **recording**, **stored object retrieval**, **bulk transfer** and **live measurement stream**; *Module Hub* and *MCI transport binding* extended. Frozen core vocabulary unchanged. The proposal's terms — USB host port, Fabric Port, fabric link — are not adopted.
  - §5.2 guidance: *pull, never push*; *two classes of MCI traffic, and where the events are* (control and bulk with the chunk as interleaving unit, AEL on separate wires); *reading a recording that is still being written* (live monitoring by polling the tail, a pushed stream remains open); *event, telemetry, recording, live stream* kept apart; *object not found*, *object changed* and *object in progress* join the error categories.
  - [Worked Example: Unattended Field Deployment](./examples/worked-example-unattended-field-deployment.md) §9 now retrieves the two per-segment recordings and the event log — inventory, chunked reads, a cable pulled halfway and resumed by offset, verification against the inventory hashes — and notes that a Hub would have forwarded the same; the deployment record lists the retrieved objects.
  - EDR-007, EDR-008 and EDR-009 open-item lists annotated; EDR-009's statement that the bulk path lies outside MCI is superseded.
  - Left open in EDR-010: the direct local transport binding (USB device class, addressing of a Hub and its Modules on one connection, chunk bound, control/bulk interleaving, host-loss supervision); `MCL` cascading; a Module-pushed live measurement stream and asynchronous notification; deletion of stored objects; retrieval during `RUNNING` as a Platform requirement; throughput figures; Hub power from the host-facing interface and other product decisions.
- **Module external interfaces and power** ([EDR-011](./docs/edr/EDR-011-module-external-interfaces-and-power.md)): one Module Port for communication, a separate Module Power Interface for primary power, USB-C as the service connection — and the principle that communication and primary Module power never share a connector.
  - `AES-MOD-005` (external interfaces and power separation) in [Architecture §3](./docs/03-architecture.md#aes-mod-005-external-interfaces-and-power-separation): at most three external interface roles on separate connectors — Module Port, Module Power Interface, direct local transport (USB-C SHOULD); at most one Module Port and no separate AEL connector; no primary power on the Module Port and no dependency on a Hub or power distributor for it; an external primary power input is a Module Power Interface at nominal 12 V DC with every rail regulated locally; USB powering optional and declared, never the required deployed power; no voltage on the power-input contacts from any other source and no back-feed onto USB or any other source; Unit managed power kept apart. `AES-HUB-001` extended: a Hub is not required to supply, and a Module Port does not carry, a Module's primary operating power. [Architecture §7](./docs/03-architecture.md#7-module-hub): the Hub is a communication device powered through its own input, a Module Power Interface input preferred; a power distributor is a separate, unspecified product.
  - Interface specification **`AURIORA Module Port`** ([`docs/interfaces/module-port.md`](./docs/interfaces/module-port.md), `0.1`, Draft): M8 8-position A-coded, female on every device, one contact assignment everywhere; contact roles `MCL_P`/`MCL_N` (half duplex, one pair), `AEL_IN_P`/`AEL_IN_N`, `AEL_OUT_P`/`AEL_OUT_N`, `GND`, `RESERVED` (not connected on any device, wired through in the cable, Platform-owned); the **AURIORA Link Cable** — male-to-male, AEL crossover with polarity preserved, `MCL`/`GND`/`RESERVED` straight, one twisted pair per link, shield to shell, non-oriented, marked; generic straight-through cables incompatible and every port survives one indefinitely with no valid frame; hub-less operation is the direct 1:1 link and Hub-to-Hub links use the same port and cable; live insertion normal; signal-only. Position numbering, cable impedance/size/length, crosstalk limits and `MCL` electricals open.
  - Interface specification **`AURIORA Module Power Interface`** ([`docs/interfaces/module-power.md`](./docs/interfaces/module-power.md), `0.1`, Draft): M8 3-position A-coded, **male input on the Module, female output on the source, male-to-female straight power cable** — the exposed-contact safety rule; positions per the insert's own numbering, **1 `MPI_VIN` (+12 V), 3 `MPI_RTN` (0 V), 4 `RESERVED`**; 12 V DC nominal; local regulation; reverse-polarity, overcurrent, transient and hot-plug protection; no back-feed in either direction; the connector rating a ceiling, never the limit. Accepted input-voltage range, current limit, cable conductor size and length open.
  - `MCL` duplex model decided: **half duplex on one differential pair, RS-485-class, Hub-polled** ([Interfaces and Versioning §5.1](./docs/05-interfaces-and-versioning.md#51-transport-bindings)); the binding — including the half-duplex line discipline (idle ownership, initiation, enables, turnaround, contention, termination topology) — remains open. **AEL stays two unidirectional pairs**: a single half-duplex AEL pair was evaluated in EDR-011 and rejected (collisions with no recovery, or a medium-access rule coupling event latency to peer traffic). [Architecture §7.1](./docs/03-architecture.md#71-the-module-port) rewritten: settled items (independent links, one connector/assignment/cable, half-duplex `MCL`, direct 1:1, no power, live insertion) and open items (position numbering, `MCL` binding, cable figures and crosstalk). §4.1: both links leave a Module through its Module Port; the direct link is one Link Cable.
  - **Terminology §3**: new supporting terms **Module Power Interface** and **AURIORA Link Cable**. The proposal's umbrella term "AURIORA Interface" is not adopted — the connector is the Module Port. Frozen core vocabulary unchanged.
  - [Interface Specifications README](./docs/interfaces/README.md) and [Document Index](./docs/document-index.md) list the two specifications; the `STANDARD.md` architecture diagram gains the Module Port and the Module Power Interface. EDR-007 and EDR-008 open-item lists annotated. [Worked Example: Multimodal AEL Experiment](./examples/worked-example-multimodal-ael-experiment.md) names the Link Cable and the per-device power inputs.
  - Left open in EDR-011: Module Port position numbering; Link Cable impedance, conductor size, shield and maximum length; `MCL`-to-AEL crosstalk; the `MCL` binding; the Module Power Interface accepted voltage range and current limit, and with them the power cable; the function of the reserved contacts; everything about a power distributor.

### Compatibility

**One incompatible change to a Draft interface specification, released within `0.9.0` under pre-Release `0.x` versioning ([AES-VER-001](./docs/05-interfaces-and-versioning.md#aes-ver-001-semantic-versioning-for-released-contracts)):** AEL `0.2` is not mechanically compatible with the M8 3-position ports of AEL `0.1`; its frame is unchanged. Nothing Released carried the `0.1` connector. Everything else in `0.9.0` is additive.

## [0.8.0] - 2026-09-17

### Changed — incompatible

- **The Module Synchronization Interface (SYNC) is superseded by the AURIORA Event Link (AEL)**, decided in [EDR-008: AURIORA Event Link](./docs/edr/EDR-008-auriora-event-link.md), which supersedes [EDR-006](./docs/edr/EDR-006-module-synchronization-interface.md) and the SYNC-related parts of [EDR-007](./docs/edr/EDR-007-module-control-interface-and-module-hub.md) (firmware-free SYNC event path, static fan-out, SYNC terminology of the Module Hub and Module Port). The MCI and `MCL` decisions of EDR-007 remain in force. Both earlier records are preserved unchanged apart from a supersession note in their Status field. The motivation is recorded in EDR-008: the single-meaning edge and the firmware-free fan-out Hub were designed for a few Modules and one deterministic instant per run, and cannot express the multimodal, closed-loop experiments — one Module originating several event types, receivers selecting events, events accepted while `RUNNING`, events crossing Hubs — that the Platform is built for.
- **[Interfaces and Versioning §4](./docs/05-interfaces-and-versioning.md#4-auriora-event-link)** is rewritten as *AURIORA Event Link* (the section keeps its number; its anchor changes). `AES-SYNC-001` to `AES-SYNC-004` are **retired** — listed in the [Document Index](./docs/document-index.md), never reused — and replaced by five requirements:
  - `AES-AEL-001` (Module-level typed event interface): an AEL event frame carries a numeric event identifier and an integrity check and nothing else — no command, parameter, payload, address, Module identity, name, timestamp or priority; meaning lives in Module bindings and the deployment record, never in the frame or its timing; AEL is not a data, measurement, telemetry, logging, firmware-update or command transport; not part of any Unit Interface Profile.
  - `AES-AEL-002` (point-to-point links, direct and routed operation): one AEL OUT to one AEL IN, receiver-terminated, no passive multidrop; the frame is identical directly, through one router or through several over Hub-to-Hub AEL links; a Module never needs to know whether a router is on the path and a Hub is never a prerequisite for two Modules to exchange events; receivers resolve to the AEL idle state on open, unpowered, shorted, inserted or removed links; no valid frame from power, reset or cabling transitions; line activity or a framing/integrity error is never an event.
  - `AES-AEL-003` (event identifiers and Module event bindings): 16-bit identifiers, `0x0000` reserved invalid/unbound, allocated by the host per deployment, unique per logical event source within the active AEL routing domain, mapping stored in the deployment record; **AEL receive bindings** map identifier → action + enabled Module Lifecycle States, none enabled before `ARMED`; action only on a complete, integrity-valid frame whose identifier is bound and enabled in the current state, everything else ignored and recorded; **`RUNNING` no longer disables reception** — acceptance while running is a per-binding decision, and restart/stop/queue/advance/phase-change are explicit configured actions; **AEL event source bindings** map the actual internal occurrence → identifier; no implicit IN→OUT forwarding; optional deterministic delay as Module configuration; bindings readable over MCI or the Host Interface.
  - `AES-AEL-004` (deterministic timing and observability): hardware-near timestamp at the start-of-frame reference instant, in local time and sample index; source-to-frame and frame-to-action latency and jitter characterized and declared per Module, forwarding latency, jitter and fan-out skew per router — AES fixes no figure and forbids "zero-delay"; no acknowledgment or retransmission; invalid frames dropped, counted and reported where received; event log of received (acted/ignored + reason), transmitted and invalid frames with timestamp, sample index, state, run identifier and local per-direction counters, never presented as synchronized.
  - `AES-AEL-005` (active Hub routing and bounded overload behavior): store-and-forward after complete validation, never forwarding an invalid frame; route table keyed by ingress port and identifier to an output set, identifier unchanged, no interpretation, merging, suppression, prioritization or retry, no experiment logic; outputs of one routing decision launched within a characterized maximum skew; documented queue capacity, deterministic arbitration, busy-output behavior, maximum event rate and overflow behavior — overflow counted and reported, never silent; route table staged, validated and committed as a whole with a readable content identity, frozen while a dependent deployment is `ARMED`/`RUNNING` except through an observable abort/fault/recovery operation, never reinstated by the router alone after power loss or reset; Hub-to-Hub AEL links carry the unchanged frame in an acyclic topology with no run-time loop mitigation; the router is host-manageable at least for identity, AEL version, capabilities and limits, staged/verified/committed route configuration, active-configuration identity and per-port state, with the concrete management contract left open.
- **[Architecture §7 Module Hub](./docs/03-architecture.md#7-module-hub)** rewritten: the Hub is a managed `MCL` concentrator + an **AEL router** (a bounded real-time subsystem with a published timing contract, which management traffic must not starve) + an optional **AEL event source**. AEL scales through Hub-to-Hub AEL links independently of the still-open `MCL` cascading question. `AES-HUB-001` now scopes the Hub to MCI transport, AEL routing and optional AEL origination, states that a route is a mapping of ports and identifiers and never a rule about meaning, and adds that two Modules remain able to exchange AEL events directly without a Hub. `AES-HUB-002` covers AEL routing in its fault-containment clause and keeps the count of Module Ports and Hub-to-Hub links out of every contract including the AEL frame. §7.1 Module Port carries `MCL` + AEL IN + AEL OUT; standalone AEL ports are retained; the crosstalk open item notes that integrity protection turns crosstalk into counted invalid frames rather than false events, and that it must still be specified.
- **[Architecture §3](./docs/03-architecture.md#3-module-design)**: a Module MAY provide AEL IN / AEL OUT ports and, if so, lists the receive actions and internal event sources it can bind.
- **`AES-MCI-003`**: capability discovery names AEL IN, AEL OUT and, for AEL, the supported AEL version, maximum receive and source bindings and the Module's declared event-rate and timing envelope. **`AES-MCI-004`**: the deterministic event is carried by AEL, never by MCI operations issued Module by Module. §5 introduction and §5.2 guidance updated (the hot-plug note now states that a Module with the declared capability may *continue* an armed or running Session without the host but never start or re-arm one on reconnection; event reception is decided by host-compiled bindings and routes, not by addressing on the wire).
- **Terminology §3**: the supporting terms *Module Synchronization Interface (SYNC)*, *SYNC event*, *SYNC Hub*, *SYNC Source*, *SYNC IN action* and *SYNC OUT source* are replaced by **AURIORA Event Link (AEL)**, **AEL event**, **AEL event identifier**, **AEL routing domain**, **AEL router**, **AEL event source**, **AEL receive binding**, **AEL event source binding** and **Hub-to-Hub AEL link**; *Module Port*, *Module Hub* and *Module Lifecycle State* are updated. Frozen core vocabulary (`AES-TERM-003`) is unchanged.

### Added

- **Autonomous Module operation and recovery** ([EDR-009](./docs/edr/EDR-009-autonomous-module-operation-and-recovery.md)), making unattended standalone operation — a Module prepared over a local cable and left to run without a host, a Module Hub or AEL — a first-class, capability-driven use of the Platform. Two requirements in [Interfaces and Versioning §5](./docs/05-interfaces-and-versioning.md#5-module-control-interface):
  - `AES-MCI-006` (autonomous continuation and deployment policy): a Module MAY declare **autonomous continuation** — continuing an `ARMED`/`RUNNING` Session to `COMPLETE` without a host; if it does, it declares the **deployment policy** behaviors it supports — host loss *continue* / *stop*, recovery after reset (`AES-MCI-007`) where it holds persistent state, storage exhaustion *stop* / *overwrite oldest* where it records locally, plus capacity and free space — and MAY declare further behaviors but has no undeclared one; a host configures the policy only from the declared set, the Module refuses anything else with a defined error and never substitutes, and the active policy is readable; host-loss detection is defined by the Module or binding, never by the Session; under *continue*, loss of host, Hub or transport and any reconnection change nothing, `COMPLETE` is reached without the host, and completion/stop status, local time and sample index, faults, event log and stored-data integrity state are preserved for readout; reconnection never re-arms, resumes or restarts; storage exhaustion is always logged, overwrite is never a default or undeclared behavior and its extent is readable; a Module without the capability is operated unchanged and nothing autonomous is inferred from product or firmware.
  - `AES-MCI-007` (recovery after reset and run segment provenance): after any reset a Module starts in `IDLE` with safe outputs and never restores `ARMED`/`RUNNING` as a remembered state; **autonomous recovery** happens only when present, integrity- and version-valid **persistent deployment state** records a recovery behavior other than *none*, the recorded configuration, Session, Assets and bindings are present with matching integrity values, the Session's prerequisites are available, the consecutive-recovery count is within the declared bound and the `AES-MCI-004` arming checks pass — then through the ordinary lifecycle transitions with recovery as the reason; otherwise the Module stays non-running with the refusal and reason recorded and its state and data preserved, and corrupt, incompatible or absent persistent state never authorizes recovery; minimum persistent-state content (deployment identity, object identities and integrity values, policy, run and segment identity, recovery count, last state and transition reason, own schema version and integrity value) with atomic update; every recovery opens a new **run segment** (*resume*: same run; *restart*: new run) whose boundary records reset cause (at minimum power-on / brownout / watchdog / software / external / unknown), last persisted and first new local time and sample index, time-reference status and the authorizing policy, and data across a boundary is never presented as continuous; in-run fault recovery is permitted where fault classes are documented as recoverable / degraded / fatal, bounded and logged; recovery occurrence, run and segment identity, reset cause and data loss or overwrite are readable through MCI.
  - `AES-MCI-003`: the minimum capability list gains **autonomous continuation**, with the declared deployment policy behaviors as its limits — the guidance and the worked example had referred to a capability the list did not contain.
  - [Architecture §3](./docs/03-architecture.md#3-module-design): a Module MAY support unattended autonomous operation as a declared capability; when declared, its Controller owns continued execution, local data handling and the configured recovery behavior while the host is absent, and neither a Module Hub nor AEL is a prerequisite. [Architecture §7](./docs/03-architecture.md#7-module-hub): a Module Hub holds no deployment policy, so a Hub-dependent unattended deployment survives a Module reset but not a Hub power loss without a host (`AES-AEL-005` unchanged; a persistent route policy is recorded as an open question).
  - **Terminology §3**: new supporting terms **autonomous continuation**, **deployment policy**, **persistent deployment state** and **run segment**; *Session* now states that how a Session is operated in an installation is the deployment policy, and *Module Lifecycle State* that a reset always begins in `IDLE`. Frozen core vocabulary unchanged.
  - §4.2 and §5.2 guidance: the host-not-in-the-timing-path bullet names the capability; the hot-plug bullet distinguishes continuation and policy-authorized recovery from reconnection; new bullets on Session versus deployment policy versus Module configuration, and on the lifecycle after a reset in one line, including a stimulus Module's right to declare *none* as its only recovery behavior; *invalid deployment policy* and *recovery refused* join the error categories.
  - Informative worked example [Unattended Field Deployment](./examples/worked-example-unattended-field-deployment.md) (`AES-EXAMPLE-AUTONOMOUS`): one Module over USB — capabilities, Session versus policy, validation and refusal, arming, host gone, a brownout recovered as segment 1, what a refused recovery looks like, storage exhaustion under *stop*, the readback three weeks later and the resulting record. All product values illustrative; APEM's actual behaviors and defaults are recorded as an open product decision in EDR-009, which also notes that no APEM product-level specification exists yet.
- Interface specification **`AURIORA AEL`** ([`docs/interfaces/ael.md`](./docs/interfaces/ael.md), version `0.1`, Draft): topology (direct, routed, multi-Hub); M8 3-position A-coded connector with pin 1 `GND`, pin 2 `AEL_P`, pin 3 `AEL_N` and the `AEL_IN_*`/`AEL_OUT_*` nets, carried over from SYNC; point-to-point differential signaling with receiver-side termination (120 Ω reference assumption), a true fail-safe receiver requirement, protection at the connector, no back-drive, no frame on power/reset/cabling transitions; the **logical idle** rule; a **settled baseline encoding** — exactly four bytes (16-bit big-endian `event_id` + CRC-16 with poly `0x1021`, init `0xFFFF`, no reflection, no xorout, check `0x29B1`), carried as UART-class 8N1 characters at a **1 Mbit/s Draft baseline**, idle = mark, frames delimited by at least two character times of idle with deterministic gap-based resynchronization and whole-frame invalidation; identifier rules; the three-instant timing model with the reference instant at the first start-bit edge after a qualifying gap and the resulting action-latency floor; the AEL router — store-and-forward, `(port, event_id)` routes, fan-out skew, queueing/arbitration/overflow, stage → validate → commit lifecycle with content identity, observability, Hub-to-Hub links with no fixed depth, timing contract; compatibility classes and tests; settled versus open items; version history. The normative electrical profile (RS-485-compatible driver/receiver contract intended), connector gender/keying, cable and termination validation, timing envelopes and the router management contract remain open. Not wire-compatible with SYNC `0.1`.
- [EDR-008: AURIORA Event Link](./docs/edr/EDR-008-auriora-event-link.md), recording the alternatives weighed — one line per event type, per-trial meaning over MCI, meaning in pulse patterns, a general message protocol; registered or textual identifiers; retaining the firmware-free fan-out, a semantics-aware Hub, cut-through forwarding; `MCL` cascading or network mechanisms for multi-Hub scaling; retaining SYNC for third-party instruments; Hub management as MCI extension, second protocol or logical requirement; inheriting the SYNC LOW idle; reusing `AES-SYNC-*`; a minor version — the deliberately accepted loss of direct oscilloscope/DAQ consumption, the list of what is architecturally settled versus open, and the companion-guide consequences. Indexed in `STANDARD.md`.
- Informative worked example [Multimodal AEL Experiment](./examples/worked-example-multimodal-ael-experiment.md) (`AES-EXAMPLE-AEL`): a closed-loop bench of APEM, AAM, an ultrasound Module and APBM on two Module Hubs — discovery, identifier allocation, Sessions and bindings, compiled route tables, stage/commit, arming, `T0`, local baseline, a detector event fanned out across Hubs, completion events acted on while `RUNNING`, an unbound event and a corrupt frame located by counter reconciliation, a host disconnect and reconnection without re-arm, and the deployment record; plus the same frame on a Hub-free pair. Replaces the SYNC worked example (`AES-EXAMPLE-SYNC`, retired).
- Document Index section **Retired Identifiers**, listing `AES-SYNC-001`–`AES-SYNC-004`, `AES-EXAMPLE-SYNC` and the `AURIORA SYNC` specification with their replacements.

### Compatibility

**Incompatible normative change, released as a `MINOR` increment under pre-Release `0.x` versioning ([AES-VER-001](./docs/05-interfaces-and-versioning.md#aes-ver-001-semantic-versioning-for-released-contracts)).** The normative model of the Module-to-Module event interface changes incompatibly: the frame now carries an identifier, the Hub routes with firmware in the event path, and `RUNNING` no longer implies ignoring events. Although the SYNC physical specification was Draft, the requirements in Interfaces and Versioning §4 and the Hub rules in Architecture §7 were normative in `0.6.0`–`0.7.1`. No Released Module or Hub exists, so no deployed artifact breaks; the number records the change of model. The Unit Interface, its three `0.1` Draft profiles, the EEPROM schema, MCI (`AES-MCI-001`, `-002`, `-005` unchanged; `-003` and `-004` reworded for AEL without changing their obligations beyond the AEL properties named), `MCL`, naming, identity and maturity rules are unaffected. The autonomous-operation addition (`AES-MCI-006`, `AES-MCI-007`, the `AES-MCI-003` list extension) is **additive**: a Module that declares no autonomous continuation, no recovery behavior and no local storage conforms without change, and the only rule that now binds every Module — start in `IDLE` after a reset, restore nothing remembered — was already implied by the ARM boundary and stated by the Firmware Style Guide. MCI has no version number yet, so none is incremented; the first binding specification carries these semantics. Companion guides: Hardware Design Guide `0.5.0`, Firmware Style Guide `0.5.0`, Software Style Guide `0.3.0` carry the corresponding implementation guidance.

## [0.7.1] - 2026-09-13

### Fixed

- **[Architecture §7.1](./docs/03-architecture.md#71-the-module-port)** — the open item describing the `MCL` duplex model enumerated only two options, half duplex on one pair and full duplex on two pairs, and stated that the duplex model determines the pair count. Both were wrong: full duplex on a *single* pair with simultaneous bidirectional transmission is an established option, so duplex model and pair count are not the same question, and the omission silently excluded a class of existing standard links from a decision that [EDR-007](./docs/edr/EDR-007-module-control-interface-and-module-hub.md) records as blocking for all `MCL` hardware work. The bullet now lists three duplex options and adds the question that is inseparable from them — whether `MCL` adopts an existing standard link or is specified from scratch. The enumeration in EDR-007's open-items list is superseded by this text; the record itself is unchanged, as required by [AES-EDR-002](./docs/08-decisions-and-governance.md#aes-edr-002-decision-record-structure-and-immutability).

### Added

- **[Architecture §7.1](./docs/03-architecture.md#71-the-module-port)** — hot-plug and live-insertion behavior of the Module Port, and the protection strategy at its contacts, added to the open items. Both are named in EDR-007 as properties belonging to the Module Port specification but were absent from the list in AES. Connecting or disconnecting a Module on a running bench must disturb no other port (`AES-HUB-002`) and must not produce a SYNC event on any link.
- **[Architecture §7](./docs/03-architecture.md#7-module-hub)** — Module Hub **cascading** recorded as open. It is settled with the `MCL` binding because it decides whether that binding's addressing is flat or hierarchical, and a binding that assumes a single Hub cannot be extended to cascading without a compatibility break. SYNC Hub cascading is already permitted by [`docs/interfaces/sync.md`](./docs/interfaces/sync.md) Section 5 and is unaffected.
- **[Interfaces and Versioning §5.2](./docs/05-interfaces-and-versioning.md#52-guidance-non-normative)** — a guidance note stating that asynchronous notification is not part of MCI in this version: every operation is a host-initiated request with a response, which covers everything AES requires, and whether a Module may report a fault unprompted is deliberately left to the first binding specification. The absence was previously implied by the repeated phrase "request/response correlation" but never stated, leaving a binding author to guess.

No requirement is added, removed or changed in this release, and no anchor changes. `AES-MCI-001` to `AES-MCI-005`, `AES-HUB-001`, `AES-HUB-002` and the amended `AES-SYNC-002` are unchanged.

## [0.7.0] - 2026-09-12

### Added

- **Module Control Interface (MCI)** — the Platform's transport-independent realization of the Host Interface, defined in a new [Interfaces and Versioning §5](./docs/05-interfaces-and-versioning.md#5-module-control-interface). Until now AES required only that a Released Host Interface be machine-parseable with a defined error model (`AES-IF-002`), which left every Module free to invent its own identity query, capability model and notion of readiness. MCI defines what a control operation *means*; how the bytes travel is an **MCI transport binding**. Five requirements:
  - `AES-MCI-001` (transport independence): a binding defines carriage only — framing, request correlation, error signaling, flow control and, for a physical link, its electrical layer — and never alters the meaning of an operation; where a Module implements MCI over more than one transport, an operation has the same meaning, preconditions and lifecycle effect on each; a binding that cannot carry an operation reports a defined error rather than substituting behavior.
  - `AES-MCI-002` (Module identity): persistent identity readable before configuration and unchanged across power cycles, transports, cables, Hub ports, device paths and enumeration order; conveys Product Family and Product, Product Revision, firmware version, serial number, MCI version and bindings, plus the AOID for a Released Module; identity is never derived from the port, Hub or device path, and topology is separate metadata.
  - `AES-MCI-003` (capability discovery): a Module declares its optional functions — Assets, Sessions, SYNC IN, SYNC OUT, event logging, firmware update — before configuration; a host queries rather than inferring from family, product number, firmware version or device type; an unsupported operation fails with a defined error, never with silent success.
  - `AES-MCI-004` (lifecycle and the ARM boundary): an observable Module Lifecycle State carrying at least `IDLE`, `CONFIGURED`, `ARMED`, `RUNNING`, `COMPLETE`, with reported transitions and refusal reasons; `ARMED` requires valid configuration, verified Assets and Session where applicable, and no blocking fault; where relative timing between Modules matters the deterministic instant is carried by SYNC and **not** by issuing an MCI operation to each Module in turn.
  - `AES-MCI-005` (object transfer integrity): staged transfer — open, transfer, verify against an integrity value covering the whole object, then commit; a partial, unverified or failed object never becomes active, selectable or reported as present; the stored object inventory is exposed so a host can determine whether a transfer is needed; an interrupted transfer leaves a defined state with any previously committed object unchanged.
- **Module Hub** — optional active-star Platform infrastructure, defined in a new [Architecture §7](./docs/03-architecture.md#7-module-hub) as a composite of three separated roles: a managed `MCL` concentrator, a firmware-free SYNC Hub function, and an optional SYNC Source. Two requirements:
  - `AES-HUB-001` (scope): the Hub is MCI transport infrastructure and SYNC distribution only; it does not own or interpret Module-specific configuration, Session or experiment semantics, is never the source of Module identity, and does not discover, configure, address or power Units; a Module remains fully serviceable — commissioning, configuration, firmware update, diagnostics, recovery — through its direct local MCI transport without a Hub.
  - `AES-HUB-002` (port independence and scale interoperability): independent link state, timeout and fault handling per Module Port, so a fault or disconnection on one port does not disturb another; port count is not encoded in MCI, in a binding or in the Module Port contract, and the same Module Port contract applies regardless of Hub size; a host supports multiple distinguishable Hubs concurrently.
- Architecture §7.1 **The Module Port**: one connector and cable carrying a Module's `MCL` together with its SYNC IN and SYNC OUT as electrically independent links. Recorded as architectural intent with the physical layer deliberately open — `MCL` duplex model, contact count, connector family, gender, keying, pinout, cable construction and length, reference and shield strategy, and the `MCL`-to-SYNC crosstalk requirement. Standalone SYNC ports are retained, so a Module Port does not replace them.
- Terminology supporting terms **Module Control Interface (MCI)**, **MCI transport binding**, **Module Control Link (MCL)**, **Module Port**, **Module Hub**, **SYNC Source**, **Module Lifecycle State**, **Asset** and **Session**.
- Architecture §3: a Module's control surface `SHOULD` be MCI rather than a private command set — a `SHOULD` in this version because no transport binding is specified yet.
- Interfaces and Versioning §5.1 (transport bindings: a direct local transport such as USB, and `MCL`; neither specified in this version, and local service is not a fallback a Module may drop) and §5.2 (non-normative guidance: desired-state orchestration, groups as a host concept, hot-plug changing nothing by itself, an early error-category set).
- [EDR-007: Module Control Interface and Module Hub](./docs/edr/EDR-007-module-control-interface-and-module-hub.md), recording the decision and the alternatives weighed — leaving the Host Interface as a quality bar, a single end-to-end control interface, a shared differential physical-link abstraction as a fourth interface class, the `CTRL` name, a fully managed Hub, two separate Hub products, passive/multidrop distribution, specifying the combined connector now, permanently separate connectors, and downstream-only SYNC through the Module Port. Indexed in `STANDARD.md`.

### Changed

- `AES-SYNC-002` amended for composite devices: where a SYNC Hub function forms part of a device such as a Module Hub, the SYNC event path `SHALL` remain independent of that device's firmware; routing, port enable and group membership `SHALL` be static configuration established before the affected Modules are armed and `SHALL NOT` be evaluated per event; passive observation — counting, timestamping — is permitted only where it cannot alter, delay or gate the regenerated event; a device that originates events acts as a *SYNC Source*, a role distinct from fan-out. This constrains composite devices and relaxes nothing.
- Interfaces and Versioning: §1 Purpose names MCI; sections *Compatibility*, *Evolution* and *Guidance* are renumbered 6–8 to make room for §5. The SYNC section keeps its `§4` number and anchor deliberately, because nine inbound links reference it, two of them from companion-guide repositories.
- *Editorial:* `STANDARD.md` Canonical Documents rows for Architecture and for Interfaces and Versioning name the Module Hub and MCI; the Primary Architecture Reference diagram shows MCI as the realization of the Host Interface and the Module Hub on the MCI and SYNC paths. The Document Index records that no MCI transport binding specification exists yet.

### Compatibility

No breaking change. The additions are new requirements, new supporting terms, two new sections and a new decision record; the `AES-SYNC-002` amendment adds obligations to a composite device class that did not previously exist and changes nothing for a standalone SYNC Hub. No existing requirement, `UIF_` signal, profile, pinout or schema field changed meaning. The three Unit Interface Profiles and the SYNC specification keep their `0.1` Draft versions. The frozen core vocabulary (`AES-TERM-003`) is unchanged — all nine additions are supporting terms.

**MCI is a `SHOULD`, not a `MUST`, for Released Modules in this version**, because no transport binding is specified and requiring MCI would require conformance to something unwritten. `AES-MOD-002` is unchanged.

**[EDR-006](./docs/edr/EDR-006-module-synchronization-interface.md) is not superseded.** Standalone SYNC ports, the M8 3-position connector, its open items and the controller-less SYNC Hub all remain in force. No new AOID taxonomy value is introduced: MCI is a Host Interface contract and uses the existing `HIF` class code. The decision is recorded in EDR-007 because introducing a Platform interface class is platform-wide (`AES-EDR-001`).

## [0.6.0] - 2026-09-11

### Added

- **Module Synchronization Interface (SYNC)** — a third interface class alongside the Host Interface and the Unit Interface: a Module-to-Module, point-to-point, RS-422-compatible differential event interface that carries a single rising-edge event and no data. Interfaces and Versioning gains a new §4 with the interface-independent rules and four requirements:
  - `AES-SYNC-001` (Module-level event interface): SYNC carries only the occurrence and timing of an event; no meaning in pulse width, count, spacing or polarity; commands and data go over a control interface; SYNC is not part of any Unit Interface Profile and a Unit neither exposes nor consumes it.
  - `AES-SYNC-002` (point-to-point links and active fan-out): one SYNC OUT to one SYNC IN per link; no passive multidrop, passive splitters or required daisy-chaining; fan-out through an active, transparent SYNC Hub that documents its propagation delay and skew; termination at the receiver only.
  - `AES-SYNC-003` (event binding, arming and default behavior): a configurable SYNC IN action executed only when armed and valid in the current state; unarmed and mid-run events are ignored and recorded by default; explicit one-shot or re-arm post-completion mode; SYNC OUT generated from a configured internal event source, never by implicit IN→OUT forwarding; optional deterministic delay as Module configuration; supported actions and sources documented per Module.
  - `AES-SYNC-004` (observability): received, transmitted and ignored events logged with local timestamp, state, reason, run identifier and a local per-direction counter that is never transmitted or presented as synchronized; configuration readable over the Host Interface.
- Interface specification **`AURIORA SYNC`** ([`docs/interfaces/sync.md`](./docs/interfaces/sync.md), version `0.1`, Draft): M8 3-position A-coded connector with pin 1 `GND`, pin 2 `SYNC_P`, pin 3 `SYNC_N` identical on SYNC IN and SYNC OUT; RS-422-compatible differential signaling with a parameter-specified full-duplex transceiver class (no part named); receiver-side ~120 Ω reference termination; fail-safe idle with no event on open, unpowered or shorted input; protection at the connector; rising edge as the event; the SYNC Hub as a controller-less receive → regenerate → distribute device with documented delay and skew, cascadable. Connector gender and keying, pulse width, cable, thresholds, protection level and latency budget are open items, so the specification is Draft.
- Terminology supporting terms **Module Synchronization Interface (SYNC)**, **SYNC event**, **SYNC Hub**, **SYNC IN action** and **SYNC OUT source**.
- Architecture §3: a Module MAY provide SYNC ports; if it does, it follows the SYNC rules and lists its supported actions and sources; SYNC is never delegated to a Unit or carried on a Unit Interface.
- Informative worked example [Module Synchronization](https://github.com/auriora-org/auriora-engineering-standard/blob/v0.7.1/examples/worked-example-module-synchronization.md) (`AES-EXAMPLE-SYNC`): trigger use with staggered delays, marker use on a continuously recording Module, an ignored mid-run retrigger, and lost-event detection by counter comparison. Indexed in `STANDARD.md` and the Document Index.
- [EDR-006: Module Synchronization Interface](./docs/edr/EDR-006-module-synchronization-interface.md), recording the decision and the alternatives weighed — a messaged protocol, meaning encoded in the pulse, automatic IN→OUT forwarding, single-ended logic, optical isolation, an RS-485 multidrop bus, passive splitters, daisy-chaining, header/BNC/M8 connectors, and reacting to every pulse versus an armed gate — together with the standard-form connector naming carve-out and the note that SYNC does not answer the PPS-class time reference need recorded in EDR-005. Indexed in `STANDARD.md`.

### Changed

- Interfaces and Versioning §3.1: the "profile-defined synchronization or auxiliary signals" entry now states that these are Unit-to-host signals within one Module and that the Module-to-Module SYNC interface is not a `UIF_` signal. Sections *Compatibility*, *Evolution* and *Guidance* are renumbered 5–7 to make room for §4; no inbound links referenced the old numbers.
- `docs/interfaces/README.md` retitled *Interface Specifications* and split into a Unit Interface Profiles part and a Module Synchronization Interface part; the Document Index section is retitled accordingly and lists `AURIORA SYNC`.
- *Editorial:* `STANDARD.md` Canonical Documents rows for Interfaces and Versioning and for the interface specifications name SYNC; the Primary Architecture Reference diagram shows the Module Synchronization Interface between Modules.

### Compatibility

No breaking change. All additions are new requirements, new supporting terms, a new Draft interface specification and a new decision record; no existing requirement, `UIF_` signal, profile, pinout or schema field changed meaning. The three Unit Interface Profiles keep their signal sets, connectors and `0.1` Draft versions. ## [0.5.0] - 2026-09-10

### Added

- EEPROM optional TLV fields **Startup Peak Duration** and **Nominal Operating Current** (`AES-EEPROM-008`). Both are informational: they let a host that wants to estimate energy, log consumption, size a battery or budget inrush work from better data than a worst-case figure, and a host `SHALL NOT` substitute either for a worst-case field in a decision that enforces a limit or authorizes power. The same paragraph fixes the units of the power records — currents in milliamperes, durations in milliseconds. Additive per `AES-EEPROM-003`; the schema major version is unchanged and existing readers are unaffected.
- Terminology supporting term **Unit Interface Host**: whatever implements the host side of a Unit Interface port — normally a Module, but also an adapter, test fixture or third-party host. Interfaces and Versioning §3.1 states the consequence: where AES writes a Unit Interface obligation on "the Module", it binds whatever implements the port, which is what makes a Unit reusable outside the Module it was designed with. Product-level safety policy is not transferred by implementing a port and stays with the Module (`AES-MOD-004`).

### Changed

- `AES-UNIT-007`: the discovery domain `SHALL` — not `MAY` — remain powered and readable from `UIF_PWR_VIN` while `UIF_PWR_EN` is LOW. The sequence already validates a Unit before enabling it, so discovery power was never optional, and the companion AHDG §6.1 already required it as a `MUST`; AES was the weaker of the two on the same fact.
- `AES-UNIT-007`: the wait for `UIF_READY` is now bounded. On expiry the host de-asserts `UIF_PWR_EN` and treats the Unit as failed rather than transacting with it. The bound is a profile or product property, not a Platform constant. This was previously stated only by `UIF-MI2C-8`, leaving the profile-independent sequence with one unbounded step.
- `AES-MOD-003`: a Released Module that accepts Units now states, alongside its supported profiles and versions, how many ports of each profile it provides, what one port supplies, and any restriction on operating those ports simultaneously. A Unit is already required to declare what it needs with numbers (`AES-UNIT-004`, `AES-EEPROM-008`); this is the other side of the same contract. Port count is explicitly not a power promise.
- [`UIF-MI2C-8`](./docs/interfaces/uif-mi2c-8.md) draft clarification: the `UIF_READY` timeout rule is referenced from `AES-UNIT-007` rather than restated, and the timeout value is added to the profile's open electrical items.

### Compatibility

No breaking change. The two EEPROM fields are optional TLV records; the Unit Interface Host term is a supporting term, not frozen core vocabulary (`AES-TERM-003`); the two `AES-UNIT-007` changes tighten a sequence no Released artifact yet implements, and the `AES-MOD-003` extension binds Released Modules, of which there are none. All three Unit Interface Profiles keep their signal sets, connectors and `0.1` Draft versions. No decision record is triggered: the change set touches no frozen vocabulary, no AOID taxonomy, no Released interface and no EEPROM schema major version (`AES-EDR-001`).

## [0.4.0] - 2026-09-10

### Added

- Unit Interface Profile **`AURIORA UIF-MI2C-8`** ([`docs/interfaces/uif-mi2c-8.md`](./docs/interfaces/uif-mi2c-8.md), version `0.1`, Draft): the default Unit Interface for **low-bandwidth Managed Units**. Eight-position 1.00 mm JST SH-family connector — `UIF-I2C-6` pins 1–6 unchanged in signal and order, plus `UIF_IRQ_N` on pin 7 as a generic open-drain event notification with the host owning the pull-up, and a second `GND` on pin 8. The two grounds sit at opposite ends of the connector: pin 2 closes a tight supply loop with pin 1, pin 8 returns the far end of the signal group, roughly halving cable ground impedance for field-wired Units and keeping every signal within three positions of a reference; both SHALL be populated end to end, cable included. All eight contacts are mandatory; only the *use* of `UIF_IRQ_N` is optional and is declared in capability metadata, so one profile serves both event-driven and polling-only Units. No `UIF_RESET_N`: the Unit controller sits inside the `UIF_PWR_EN`-switched domain, so a power cycle is the stronger recovery and firmware update is a Unit API operation. The profile also fixes the Managed-I²C clock-stretch contract, bus-recovery obligation and power-sequencing detail. Electrical and mechanical limits are open, so the profile stays Draft.
- `AES-IF-009` (Unit Interface I2C address allocation): the discovery EEPROM block `0x50`–`0x57` is reserved Platform-wide with `0x50` as default; a Unit's functional address lies outside it and outside the I²C reserved addresses; a Managed Unit declares its Unit API address in EEPROM and a host never infers or hard-codes it; a host sharing one bus across Unit ports resolves collisions and leaves `UIF_PWR_EN` LOW for a colliding Unit.
- `AES-IF-010` (Unit Interface Profile selection): a Managed Unit `SHOULD` use `UIF-MI2C-8` by default and `UIF-MSPI-14` where throughput, latency, deterministic transfer timing or continuous streaming makes I²C unsuitable; a Passive or simple Unit `SHOULD` use `UIF-I2C-6`. Accompanied by a criteria table (determinism, streaming, latency, payload and update rate, event frequency, transaction count, power, connector and cabling, reset need) — no arbitrary byte-rate threshold.
- Interfaces and Versioning §3.2 *Profile Family and Selection*: the management-model × transport matrix making explicit that **Managed does not imply SPI**, and the profile identifier pattern `UIF-[M]<transport>-<positions>` (§3.1).
- EEPROM optional TLV field **Unit API Transport Address**, mandatory for a Managed Unit whose Unit API shares an addressed transport with discovery (`AES-EEPROM-008`). Additive per `AES-EEPROM-003`; existing readers are unaffected.
- Informative worked example [Choosing a Unit Interface Profile](./examples/worked-example-unit-interface-profile-selection.md) (`AES-EXAMPLE-UIF-SELECTION`): AEU, ASU, the Soil Unit and the Communication & Timing Unit assessed against `AES-IF-010`, with ASU worked end to end. Indexed in `STANDARD.md` and the Document Index.
- [EDR-005: A Low-Bandwidth Managed Unit Interface Profile](./docs/edr/EDR-005-low-bandwidth-managed-unit-interface.md), recording the decision and the alternatives weighed — reusing `UIF-MSPI-14`, widening `UIF-I2C-6` unchanged, split polling/interrupt profiles, a 7-position variant with a single ground, the chosen 8-position profile, an 8-position variant spending the contact on `UIF_RESET_N` instead, and mandatory versus optional event signalling — with AEU, ASU, the Soil Unit and the Communication & Timing Unit as validation cases. Indexed in `STANDARD.md`.

### Changed

- Architecture §5.1 renamed *Execution Models and Transport* and extended: the execution model fixes the host contract, the transport fixes the Unit Interface Profile, and the two are independent. `AES-UNIT-006` rationale extended accordingly. Terminology entries for *Managed Unit* and *Unit Interface Profile* state the same separation.
- Interfaces and Versioning §3.1: `UIF_SPI_*` described as a transport rather than as the Managed-Unit bus, and `UIF_IRQ_N` / `UIF_RESET_N` split into separate entries with their profile-independent meanings.
- [`UIF-I2C-6`](./docs/interfaces/uif-i2c-6.md) scope clarified as management-model-based, directing Managed Units to `UIF-MI2C-8` or `UIF-MSPI-14`; functional I²C addressing bound to `AES-IF-009`. The +3V3 nominal `UIF_PWR_VIN` working assumption is retained across UIF profiles and remains non-normative.
- **The Managed SPI profile is renamed `UIF-MSPI-14`** and its specification moved from `docs/interfaces/managed-spi.md` to [`docs/interfaces/uif-mspi-14.md`](./docs/interfaces/uif-mspi-14.md). - [EDR-003](./docs/edr/EDR-003-uif-mspi-connector-and-pin-assignment.md) Status annotated: its connector and pin assignment stand; its AEU-01 consequence is superseded by EDR-005 and its open identifier item is resolved to `UIF-MSPI-14`.
